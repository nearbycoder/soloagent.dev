Deploy on Railway

Getting started

soloagent needs Node 22.19 or newer. Clone the repository, install dependencies, and link the soloagent command. The terminal UI starts an embedded local server for you, with its data in ~/.soloagent:

git clone https://github.com/nearbycoder/soloagent.dev
cd soloagent.dev
npm install && npm link -w @soloagent/cli
soloagent

To use the web dashboard locally, run npm run build once and then soloagent serve. It listens on http://localhost:7420 and prints the admin token on start.

A fresh install has one agent and the built-in demo model, so you can look around without any account. The demo model only echoes and explains; it's there so the whole product works before you connect a real model.

Connect a real model

Inside the TUI, sign in with your Claude Pro or Max subscription:

soloagent TUI
/login anthropic

Your browser opens the provider's sign-in page. When it finishes, your agents can use the subscription. You can do the same from your shell, or use an API key from the dashboard instead.

soloagent login anthropic

Other ways to run it

shell
# Run the server with the web dashboard on http://localhost:7420
soloagent serve

# One-shot answers for scripts and pipes
soloagent ask "Summarize the open incidents"
git diff --staged | soloagent ask "Write a commit message for this diff"

# Point the TUI at a remote server
soloagent connect https://solo.example.com --token $SOLOAGENT_TOKEN
Next: to share agents with your team in Slack, Discord, or Telegram, run soloagent on a server. Deploy on Railway takes a few minutes.

Deploy on Railway

soloagent runs as one service with one volume. Everything it stores (threads, memory, schedules, sealed credentials) lives in that volume.

  1. Create the service

    Click Deploy on Railway, or create a new Railway service from the GitHub repo.

  2. Attach a volume at /data

    Add a volume to the service and mount it at /data. soloagent uses the Railway volume as its data directory by default, so durable runs and credentials survive redeploys.

  3. Set the environment variables

    Both are optional, but setting them yourself is recommended:

    VariableWhat it does
    SOLOAGENT_TOKENThe admin token for the dashboard, TUI, and API. If unset, one is generated on first boot, stored, and printed in the logs.
    SOLOAGENT_SECRETSeals provider credentials and connector tokens at rest. If unset, a random secret is generated and stored in the data directory. Keep it stable: credentials sealed with one secret can't be opened with another.
    SOLOAGENT_DATA_DIRWhere data lives. Defaults to the Railway volume mount path (for example /data).
    PORTHTTP port. Railway sets this for you; the default is 7420.
    generate strong values
    openssl rand -base64 32

  4. Give it a public domain

    In the service's networking settings, generate a domain. Slack works without one (Socket Mode), but you'll want it for the dashboard, webhooks, and remote TUI.

  5. Find the token in the logs

    After the deploy, open the service logs. soloagent prints a banner with its URL and token:

    deploy logs
      soloagent is up — https://solo-production.up.railway.app
    data      /data
    token     solo_••••••••••••••••••••••••
    terminal  soloagent connect https://solo-production.up.railway.app --token <token>

    If you set SOLOAGENT_TOKEN, the log says (from SOLOAGENT_TOKEN) instead of printing it.

  6. Open the dashboard

    Visit your domain, paste the token, and you're in. From there, connect a provider, create agents, and add connectors.

Docker or Node, anywhere else

soloagent isn't tied to Railway. Any host that can run a Docker container or Node 22+ with a persistent directory works. Set the same variables and point SOLOAGENT_DATA_DIR at persistent storage:

shell
export SOLOAGENT_TOKEN=…
export SOLOAGENT_SECRET=…
export SOLOAGENT_DATA_DIR=/var/lib/soloagent
soloagent serve

Providers & subscriptions

soloagent reaches models through @earendil-works/pi-ai. You can sign in with a consumer subscription over OAuth, or paste an API key. Each agent picks its own provider and model.

Sign in with a subscription

Open Providers in the dashboard and choose Sign in next to one of:

Claude Pro / Max ChatGPT GitHub Copilot SuperGrok / X Premium OpenRouter and others

The provider's sign-in page opens in a new tab. When the server runs on your own machine, the login completes on its own.

Server running remotely? Some providers redirect back to a localhost address after sign-in, which can't reach a server on Railway. When that happens, the page in your browser may fail to load. That's expected: copy the code shown by the provider, or the full URL from the address bar, and paste it into the prompt in the dashboard.

From the terminal, /login <provider> in the TUI and soloagent login <provider> in your shell run the same flow.

API keys

Paste a key under Providers for any of 30+ providers, including Anthropic, OpenAI, Google Gemini, Mistral, Groq, DeepSeek, xAI, OpenRouter, Vercel AI Gateway, Amazon Bedrock, Azure, Together, Fireworks, Cerebras, and Hugging Face. Over the API, use PUT /api/providers/:id/key.

Keys and OAuth tokens are sealed with AES-256-GCM before they're written to disk. See Security.

Subscription sign-in is subject to each provider's terms. Product names are trademarks of their respective owners.

Agents & skills

An agent is a named assistant with its own personality, model, and abilities. Create and edit them under Agents in the dashboard, or with POST /api/agents.

FieldDescription
Name & @handleThe handle is how you address it in chat: @coder. Lowercase letters, digits, and dashes.
Avatar & colorA single glyph or emoji and an accent color, shown in the dashboard and TUI.
InstructionsThe system prompt: who it is, how it should behave, what it knows.
ModelAny connected provider and model. Different agents can use different providers.
Thinking leveloff, minimal, low, medium, high, or xhigh on models that support reasoning.
SkillsThe tool sets it may use (below).
DefaultThe default agent answers anything not addressed to a specific agent.

Skills

Memory

Long-term notes about people, preferences, and facts, kept per agent across every conversation.

rememberrecallforget
Web

Fetch and read web pages and APIs, and search the web.

web_fetchweb_search
Delegate

Hand a sub-task to another agent and wait for its answer. The hand-off runs as a durable child conversation.

ask_agent
Schedule

Durable reminders and follow-ups. They sleep in storage and fire even after restarts.

schedule_reminder
Workspace powerful

Read, write, and edit files and run shell commands in a private workspace folder on the server. Only enable it for agents that trusted people can reach.

readwriteeditbash

Connectors

Connectors put your agents into chat apps. Add them under Connections in the dashboard, which includes these setup guides. Each connector can be bound to an agent; otherwise the default agent answers. In chat apps, replies stream live by editing a placeholder message as the answer arrives.

Slack

Slack uses Socket Mode, so no public URL is needed. It works on Railway and on your laptop alike.

  1. Create the app from a manifest

    Go to api.slack.com/apps → Create New App → From a manifest, pick your workspace, and paste the manifest below.

  2. Create an app-level token

    Basic Information → App-Level Tokens → Generate with the connections:write scope. Copy the xapp-… token.

  3. Install and copy the bot token

    Install App to your workspace and copy the Bot User OAuth Token (xoxb-…).

  4. Connect and invite

    Paste both tokens into a new Slack connector. Invite the bot to a channel with /invite @Solo, then mention it. DMs work too.

slack-manifest.yaml
display_information:
  name: Solo
  description: Your agents, on soloagent.dev
  background_color: "#0b0b12"
features:
  app_home:
    messages_tab_enabled: true
    messages_tab_read_only_enabled: false
  bot_user:
    display_name: Solo
    always_online: true
oauth_config:
  scopes:
    bot:
      - app_mentions:read
      - chat:write
      - channels:read
      - groups:read
      - im:history
      - im:read
      - im:write
      - users:read
settings:
  event_subscriptions:
    bot_events:
      - app_mention
      - message.im
  interactivity:
    is_enabled: false
  org_deploy_enabled: false
  socket_mode_enabled: true
  token_rotation_enabled: false

Discord

  1. Create an application

    Open the Discord Developer Portal → New Application.

  2. Get the bot token

    On the Bot tab, click Reset Token and copy it. Turn on Message Content Intent under Privileged Gateway Intents.

  3. Invite the bot

    OAuth2 → URL Generator: select the bot scope and the permissions Send Messages, Send Messages in Threads, Read Message History, and View Channels. Open the generated URL to add the bot to your server.

  4. Connect

    Paste the token into a new Discord connector. Mention the bot, reply to it, or DM it.

Telegram

  1. Create a bot

    Message @BotFather on Telegram and send /newbot. Pick a name and username; BotFather replies with a token.

  2. Connect

    Paste the token into a new Telegram connector, then message your bot.

  3. Groups and topics

    Add the bot to a group and mention it or reply to it. Forum topics each get their own conversation. Use /setprivacy in BotFather to control what the bot can see.

Webhook

Wire agents into anything that can send an HTTP request. Create a Webhook connector with a shared secret; callers send it in the x-solo-secret header.

shell
curl -X POST https://solo.example.com/api/hooks/<connector-id> \
  -H 'x-solo-secret: YOUR_SECRET' \
  -H 'content-type: application/json' \
  -d '{"text": "@coder what changed in the last deploy?", "thread": "deploys", "user": "ci"}'
Body fieldMeaning
textThe message. Routing works as in chat, so @coder … picks an agent.
threadKeeps a conversation going across requests. Omit it for a one-off.
userA display name for the sender.
callback_urlOptional. Without it, the request waits and returns { "answer": "…" }. With it, the request returns 202 right away and the answer is POSTed to that URL as { "thread", "text" }.

Chat routing & commands

Every inbound message, from any connector, is routed to one agent:

  1. If it starts with @handle or handle:, that agent answers. @coder fix the build and coder: fix the build are the same.
  2. Otherwise, the agent bound to the connector answers.
  3. Otherwise, the default agent answers.

Steering

If you send another message while an agent is still working, it steers the run in progress: the agent sees your new message right away and adjusts, rather than finishing first and answering later.

Chat commands

!resetStart a fresh conversation in this thread or DM.
!stopStop the agent's current run.
!helpShow help for routing and commands.

HTTP API & SDK

The dashboard and TUI use the same public API, so anything they do, your scripts can do. All routes live under /api and require the admin token as a bearer token, except inbound webhooks, which carry their own secret.

shell
curl https://solo.example.com/api/agents \
  -H "authorization: Bearer $SOLOAGENT_TOKEN"

Routes

GETPOST/api/agentsList or create agents.
GETPOST/api/threadsList or create threads. Create takes { agentId, title }.
POST/api/threads/:id/messagesSend a message. Returns 202 with a submissionId; follow progress over the WebSocket.
POST/api/threads/:id/askSend a message and wait for the answer: { status, answer }.
GET/api/providersList providers, their models, and which are configured.
POST/api/providers/:id/loginStart an OAuth or API-key login flow.
GETPOST/api/connectorsList or create connectors.
POST/api/hooks/:idInbound webhook. Authenticated by x-solo-secret, not the admin token.
WS/api/wsLive events. Pass the token as ?token=.

WebSocket events

Connect to /api/ws and send { "type": "subscribe", "threadId": "…" } to receive a thread's thread.snapshot, thread.messages, and thread.live events (streaming text, thinking, and tool calls). Send { "type": "tasks.subscribe" } for the live durable task graph. Server-wide events such as thread.updated, agent.updated, and connector.updated arrive without subscribing.

TypeScript SDK

@soloagent/client is a typed client for the REST API and WebSocket. It runs in Node 22+ and browsers.

ask.ts
import { SoloClient } from "@soloagent/client";

const solo = new SoloClient({
  baseUrl: "https://solo.example.com",
  token: process.env.SOLOAGENT_TOKEN,
});

const thread = await solo.createThread({ agentId: "coder" });

// Wait for the full answer
const result = await solo.ask(thread.id, "What changed in the last deploy?");
console.log(result.answer);

// Or fire and forget, and follow along live
await solo.send(thread.id, "Now draft release notes");
stream.ts
const stream = solo.connect(); // reconnects automatically
stream.subscribe(thread.id);

stream.on((event) => {
  if (event.type === "thread.live") render(event.live);         // streaming text, thinking, tools
  if (event.type === "thread.messages") append(event.messages); // committed messages
});

// later
stream.close();

Embed the core

The runtime is a library too. Open it against a data directory and use it in-process, without the HTTP server.

embed.ts
import { SoloAgent } from "@soloagent/core";

const solo = await SoloAgent.open({ dataDir: "./data" });
// … create agents and threads, send messages …
await solo.close();

Durability

Agent runs execute on @earendil-works/pi-durable, Pi's durable execution harness, backed by SQLite in your data directory.

  • Commit before show. Each model turn and each tool call is recorded as a durable step and committed before it's shown in any UI or chat app. What you see has already been saved.
  • Resume after a crash. If the process exits mid-run (a crash, a restart, a deploy), the run resumes from its last committed step when the server starts again. Completed steps aren't repeated.
  • Durable sleep. Scheduled reminders are durable timers. They wait in storage, not in memory, so they still fire after restarts.
  • Durable delegation. ask_agent starts a child conversation that is itself durable. The parent waits for it, across restarts if needed.
  • Visible. The dashboard shows the live durable task graph and upcoming schedules.
Keep the data directory. Durability is only as good as the storage behind it. On Railway, that's the volume at /data. Elsewhere, make sure SOLOAGENT_DATA_DIR points at persistent storage.

Security

  • One admin token. The dashboard, TUI, API, and WebSocket all require SOLOAGENT_TOKEN. Treat it like a password. The dashboard keeps it in an HTTP-only session cookie.
  • Sealed credentials. Provider keys, OAuth tokens, and connector tokens are encrypted at rest with AES-256-GCM, using a key derived from SOLOAGENT_SECRET.
  • Webhook secrets. Each webhook connector has its own shared secret, sent in x-solo-secret. It grants only that connector's access.
  • Workspace is powerful. The Workspace skill can run shell commands on your server. Only enable it for agents that trusted people can reach, and remember that anyone who can message a connector can talk to its agent.
  • Your data stays with you. Threads, memory, schedules, and credentials live in your data directory. Model calls go directly from your server to the providers you connect.
