Getting started

soloagent is one Node.js program. Run it on your laptop to try it, then put the same thing on a server when your team should reach it from Slack, Discord, or Telegram. Pick whichever install fits:

Install on your machine

With Node 22.19 or newer, the installer puts the soloagent command on your path:

curl -fsSL https://soloagent.dev/install.sh | sh

It downloads the latest release and installs it with npm, so you can also do that yourself, on any OS including Windows, or try it once without installing. --allow-remote=root lets npm 12 install from a release URL; older npm versions ignore it:

npm
# install
npm install -g --allow-remote=root https://github.com/nearbycoder/soloagent.dev/releases/latest/download/soloagent.tgz

# or run once, nothing installed
npx -y --allow-remote=root https://github.com/nearbycoder/soloagent.dev/releases/latest/download/soloagent.tgz

No Node? Use Docker, one command, any OS:

docker run -d --name soloagent -p 7420:7420 -v soloagent:/data ghcr.io/nearbycoder/soloagent.dev

Then open http://localhost:7420 and paste the token from docker logs soloagent.

First run

shell
# the terminal UI, with a private server and data in ~/.soloagent
soloagent

# or the web dashboard on http://localhost:7420
soloagent serve
soloagent token   # paste this into the dashboard

A fresh install has one agent and the built-in demo model, so everything works before you connect an account. Then sign in to a real model, for example your Claude Pro or Max subscription, with /login anthropic in the TUI, soloagent login anthropic in your shell, or the Providers page of the dashboard.

more examples
# one-shot answers for scripts; piped input is added after the message
git diff --staged | soloagent ask "Write a commit message for this diff"

# point the TUI at a server you deployed
soloagent connect https://solo.example.com --token $SOLOAGENT_TOKEN

Deploy

soloagent needs three things from a host: a long-running process (chat connectors hold open connections and durable timers need a clock), a persistent directory for its two SQLite databases, and, for the dashboard and webhooks, an HTTP port. It runs as a single instance; don't scale it horizontally.

Docker

The image ghcr.io/nearbycoder/soloagent.dev is built for amd64 and arm64 (so Apple silicon, Raspberry Pi, and Graviton work too). The repository's docker-compose.yml is all you need:

shell
curl -fsSLO https://raw.githubusercontent.com/nearbycoder/soloagent.dev/main/docker-compose.yml
docker compose up -d
docker compose logs soloagent | grep token

Data lives in the compose file's soloagent-data volume. To choose your own token and secret, put them in a .env file next to the compose file (see .env.example). Update with docker compose pull && docker compose up -d. Self-hosted platforms such as Coolify and Dokploy can deploy the same compose file from the repository.

Put a reverse proxy in front for HTTPS on a public server. With Caddy it is one line: solo.example.com { reverse_proxy localhost:7420 }.

Railway

  1. Create the service

    At railway.com/new, choose GitHub Repository and pick your fork, or paste https://github.com/nearbycoder/soloagent.dev and choose Deploy Repo. The Dockerfile and railway.json are picked up automatically.

  2. Add a volume at /data

    soloagent uses the volume as its data directory automatically.

  3. Set variables and a domain

    Set SOLOAGENT_TOKEN and SOLOAGENT_SECRET, generate a domain, and open it.

Render

The repository includes a render.yaml Blueprint: one Docker web service with a 1 GB persistent disk at /data, a health check, and a generated token and secret. Disks need a paid instance (Starter or above).

Deploy to Render

After the deploy, read SOLOAGENT_TOKEN from the service's Environment tab and open the onrender.com URL.

Fly.io

The included fly.toml runs one always-on machine with a volume mounted at /data:

shell
git clone https://github.com/nearbycoder/soloagent.dev && cd soloagent.dev
fly launch --copy-config --no-deploy
fly volumes create soloagent_data --size 1
fly secrets set SOLOAGENT_TOKEN=$(openssl rand -base64 32) SOLOAGENT_SECRET=$(openssl rand -base64 32)
fly deploy

Create the volume in the same region as the app. Auto-stop is off on purpose: Slack, Discord, and Telegram connections and scheduled reminders need the process running.

Linux server with systemd

shell
sudo useradd --system --create-home --home-dir /var/lib/soloagent soloagent
sudo npm install -g --allow-remote=root https://github.com/nearbycoder/soloagent.dev/releases/latest/download/soloagent.tgz
sudo curl -fsSLo /etc/systemd/system/soloagent.service https://raw.githubusercontent.com/nearbycoder/soloagent.dev/main/deploy/soloagent.service
sudo systemctl enable --now soloagent
sudo journalctl -u soloagent | grep token

Optional settings go in /etc/soloagent.env (for example SOLOAGENT_TOKEN=…).

Configuration

VariableWhat it does
SOLOAGENT_TOKENAdmin token for the dashboard, TUI, and API. If unset, one is generated on first boot, stored, and printed in the logs.
SOLOAGENT_SECRETSeals provider credentials and connector tokens at rest. If unset, one is generated and kept in the data directory. Keep it stable: credentials sealed with one secret can't be opened with another.
SOLOAGENT_DATA_DIRWhere data lives. The Docker image uses /data, so mount your volume there. soloagent serve defaults to ~/.soloagent/data; --data overrides it.
PORTHTTP port, default 7420. Most hosts set it for you. soloagent serve --port overrides it.
SOLOAGENT_DEMO0 hides the built-in demo model.
SOLOAGENT_PUBLIC_URLThe public address printed at startup. Railway's domain is detected automatically.

The server prints its URL and token when it starts:

logs

    data      /data
    token     solo_••••••••••••••••••••••••

Where it doesn't fit

Serverless and edge platforms (Vercel functions, Netlify, Cloudflare Workers, AWS Lambda) and hosts without persistent disks (Heroku's dynos, DigitalOcean App Platform) can't run soloagent: they stop the process between requests and discard its files. Use one of the options above, or any VM.

Providers & subscriptions

soloagent reaches models through @earendil-works/pi-ai. You can sign in with a consumer subscription (or an OpenRouter account) over OAuth, or paste an API key. Each agent picks its own provider and model.

Sign in with your account

Open Providers in the dashboard and choose Sign in next to one of:

Claude Pro / Max ChatGPT GitHub Copilot SuperGrok / X Premium OpenRouter and others

The provider's sign-in page opens in a new tab. When the server runs on your own machine, the login completes on its own.

Server running remotely? Some providers redirect back to a localhost address after sign-in, which can't reach a server running somewhere else. When that happens, the page in your browser may fail to load. That's expected: copy the code shown by the provider, or the full URL from the address bar, and paste it into the prompt in the dashboard.

From the terminal, /login <provider> in the TUI and soloagent login <provider> in your shell run the same flow.

API keys

Paste a key under Providers for any of 40+ providers, including Anthropic, OpenAI, Google Gemini, Mistral, Groq, DeepSeek, xAI, OpenRouter, Vercel AI Gateway, Amazon Bedrock, Azure, Together, Fireworks, Cerebras, and Hugging Face. Over the API, send { "key": "…" } to PUT /api/providers/:id/key, or run soloagent login <provider> --key.

Keys and OAuth tokens are sealed with AES-256-GCM before they're written to disk. See Security.

Subscription sign-in is subject to each provider's terms. Product names are trademarks of their respective owners.

Agents & skills

An agent is a named assistant with its own personality, model, and abilities. Create and edit them under Agents in the dashboard, or with POST /api/agents.

FieldDescription
Name & @handleThe handle is how you address it in chat: @coder. Lowercase letters, digits, and dashes.
Avatar & colorA single glyph or emoji and an accent color, shown in the dashboard and TUI.
InstructionsThe system prompt: who it is, how it should behave, what it knows.
ModelAny connected provider and model. Different agents can use different providers.
Thinking leveloff, minimal, low, medium, high, or xhigh on models that support reasoning.
SkillsThe tool sets it may use (below). New agents get every skill except Workspace.
Max turnsThe most tool rounds one run may take, 40 by default.
DefaultThe default agent answers anything not addressed to a specific agent.

Connectors

Connectors put your agents into chat apps. Add them under Connections in the dashboard, which includes these setup guides. Each connector can be bound to an agent; otherwise the default agent answers. In chat apps, replies stream live by editing a placeholder message as the answer arrives.

Slack

Slack uses Socket Mode, so no public URL is needed. It works on any server and on your laptop alike.

  1. Create the app from a manifest

    Go to api.slack.com/apps → Create New App → From a manifest, pick your workspace, and paste the manifest below.

  2. Create an app-level token

    Basic Information → App-Level Tokens → Generate with the connections:write scope. Copy the xapp-… token.

  3. Install and copy the bot token

    Install App to your workspace and copy the Bot User OAuth Token (xoxb-…).

  4. Connect and invite

    Paste both tokens into a new Slack connector. Invite the bot to a channel with /invite @Solo, then mention it. DMs work too.

display_information:

features:
  app_home:
    messages_tab_enabled: true
    messages_tab_read_only_enabled: false
  bot_user:
    display_name: Solo
    always_online: true
oauth_config:
  scopes:
    bot:
      - app_mentions:read
      - chat:write
      - channels:read
      - groups:read
      - im:history
      - im:read
      - im:write
      - users:read
settings:
  event_subscriptions:
    bot_events:
      - app_mention

  interactivity:
    is_enabled: false
  org_deploy_enabled: false
  socket_mode_enabled: true
  token_rotation_enabled: false

Discord

  1. Create an application

    Open the Discord Developer Portal → New Application.

  2. Get the bot token

    On the Bot tab, click Reset Token and copy it. Turn on Message Content Intent under Privileged Gateway Intents.

  3. Invite the bot

    OAuth2 → URL Generator: select the bot scope and the permissions Send Messages, Send Messages in Threads, Read Message History, and View Channels. Open the generated URL to add the bot to your server.

  4. Connect

    Paste the token into a new Discord connector. Mention the bot, reply to it, or DM it. Each channel, thread, and DM is its own conversation.

Telegram

  1. Create a bot

    Message @BotFather on Telegram and send /newbot. Pick a name and username; BotFather replies with a token.

  2. Connect

    Paste the token into a new Telegram connector, then message your bot.

  3. Groups and topics

    Add the bot to a group and mention it or reply to it. Forum topics each get their own conversation. Use /setprivacy in BotFather to control what the bot can see.

Webhook

Wire agents into anything that can send an HTTP request. Create a Webhook connector with a shared secret; callers send it in the x-solo-secret header.

shell
curl -X POST https://solo.example.com/api/hooks/<connector-id> \
  -H 'x-solo-secret: YOUR_SECRET' \
  -H 'content-type: application/json' \
  -d '{"text": "@coder what changed in the last deploy?", "thread": "deploys", "user": "ci"}'
Body fieldMeaning
textThe message. Routing works as in chat, so @coder … picks an agent.
threadKeeps a conversation going across requests. Omit it for a one-off.
userA display name for the sender.
callback_urlOptional. Without it, the request waits and returns { "thread", "status", "answer" }. With it, the request returns 202 with { "accepted": true, "thread" } right away, and the answer is POSTed to that URL as { "thread", "text" }, with the same x-solo-secret header so you can check it came from soloagent.

Chat routing & commands

Every inbound message, from any connector, is routed to one agent:

  1. If it starts with @handle or handle:, that agent answers. @coder fix the build and coder: fix the build are the same.
  2. Otherwise, the agent bound to the connector answers.
  3. Otherwise, the default agent answers.

Addressing applies to that one message, and each agent keeps its own conversation in a chat thread.

Steering

If you send another message while an agent is still working, it steers the run in progress: the agent sees your new message after its current step (a model reply or a round of tool calls) and adjusts, rather than finishing the whole task first and answering later.

CommandWhat it does
!agentsList the agents you can talk to and their handles.
!resetStart a fresh conversation in this thread or DM. !new does the same.
!stopStop the agent's current run.
!helpShow help for routing and commands.

Automations

An automation is a prompt that runs on a schedule: “every weekday at 9:00, post a standup summary in #eng”, “every Monday, summarize last week's deploys”, “every hour, check the status page and alert if anything is down”. Reminders fire once; automations repeat.

Create them under Automations in the dashboard, with POST /api/automations, or by asking an agent that has the Schedule skill. In Slack:

slack
@solo every weekday at 9 post the open incidents here

The agent calls schedule_recurring. It can also list_automations and cancel_automation.

Schedules

A schedule is a 5-field cron expression read in an IANA time zone (the server's by default). The dashboard also offers simple presets, which are stored as cron:

Preset or phraseCron
every 15 minutes*/15 * * * *
every 2 hours0 */2 * * *
daily at 17:3030 17 * * *
weekdays at 9:000 9 * * 1-5
mondays at 9:3030 9 * * 1

The fields are minute, hour, day of month, month, and day of week. Each takes *, numbers, lists (1,15), ranges (1-5), and steps (*/10); months and days also take names (jan, mon-fri). As in classic cron, when both day fields are set, a day matching either one fires. @hourly, @daily, @weekly, and @monthly work too.

Daylight saving time. A time skipped by a spring-forward jump (02:30 on that night in most of the US) fires once, at the moment of the jump. A time repeated by a fall-back fires once, on its first occurrence.

Where runs land

  • A thread. Pick any existing thread, web or chat. Each run is a message from Automation: <name> in that thread, answered by the thread's agent. In a chat thread the answer is posted to Slack, Discord, or Telegram like any other reply.
  • A chat channel. Pick a connection and a channel id (Slack channel id, Discord channel id, Telegram chat id, or a webhook callback URL). Each run posts a new top-level message in the channel; on Slack, replies to it start a normal thread with the agent. The automation keeps one conversation of its own, so the agent remembers earlier runs (“since yesterday…”).

Catch up once

Each enabled automation is a durable task that sleeps until its next run. If the server is down when a run is due, that run fires once when the server starts again, and the schedule continues from then. Missed runs are not replayed one by one: an hourly automation that was down for a day runs once on startup, not 24 times.

Disabling, editing, or deleting an automation cancels or reschedules its task immediately. Run now runs it once outside its schedule, even when it is disabled. Runs use the same path as a chat message, so the agent's model, skills, and limits apply.

API

shell
curl https://solo.example.com/api/automations \
  -H "authorization: Bearer $SOLOAGENT_TOKEN" -H "content-type: application/json" \
  -d '{
    "name": "Standup summary",
    "prompt": "Summarize the PRs merged since the last run and the open incidents.",
    "preset": { "kind": "weekdays", "time": "09:00" },
    "timezone": "America/Chicago",
    "target": { "kind": "channel", "connectorId": "sla_…", "channel": "C0123456789", "location": "#eng" }

Give cron (an expression or a phrase like "weekdays at 9:00") or preset. A thread target is { "kind": "thread", "threadId": "thr_…" }. List them from the terminal with soloagent automations.

Terminal UI

soloagent opens a full-screen terminal UI built on pi-tui. With no arguments it uses a local server, starting one in-process if soloagent serve isn't already running; after soloagent connect <url> --token … it talks to that remote server instead. HTTP API & SDK

The dashboard and TUI use the same public API, so anything they do, your scripts can do. All routes live under /api and require the admin token in an authorization: Bearer … header, except inbound webhooks, which carry their own secret. Only the WebSocket accepts the token as ?token=; REST routes reject it. Requests without a valid token get 401.

shell
curl https://solo.example.com/api/agents \
  -H "authorization: Bearer $SOLOAGENT_TOKEN"

Routes

GETPOST/api/agentsList or create agents.
GETPOST/api/threadsList or create threads. Create takes { agentId, title }, both optional; agentId can be an id or a handle.
POST/api/threads/:id/messagesSend { text }. Returns 202 with a submissionId; follow progress over the WebSocket.
POST/api/threads/:id/askSend { text } and wait for the answer: { status, answer }, or { status: "unanswered", reason }.
GET/api/providersList providers, their models, and which are configured.
POST/api/providers/:id/loginStart a login flow: { type: "oauth" } (the default) or { type: "api_key" }.
PUT/api/providers/:id/keySave an API key: { key }.
GETPOST/api/connectorsList or create connectors. Create takes { kind, name, agentId, config }; a webhook's config is { secret }.
GETPOST/api/automationsList or create automations.
PATCHDELETE/api/automations/:idEdit (including { enabled }) or delete an automation.
POST/api/automations/:id/runRun an automation once now.
GET/api/automations/preview?cron=&tz=The schedule in words and its next 5 run times.
POST/api/hooks/:idInbound webhook. Authenticated by x-solo-secret, not the admin token.
WS/api/wsLive events. Pass the token as ?token=.

WebSocket events

Connect to /api/ws and send { "type": "subscribe", "threadId": "…" } to receive a thread's thread.snapshot, thread.messages, and thread.live events (streaming text, thinking, and tool calls). Send { "type": "tasks.subscribe" } for the live durable task graph. Server-wide events such as thread.updated, agent.updated, connector.updated, and automation.updated arrive without subscribing.

TypeScript SDK

@soloagent/client, in packages/client, is a typed client for the REST API and WebSocket with no dependencies. It runs in Node 22.19+ and in browsers. It isn't on npm yet, so use it from a clone of the repository.

ask.ts
import { SoloClient } from "@soloagent/client";

const solo = new SoloClient({
  baseUrl: "https://solo.example.com",
  token: process.env.SOLOAGENT_TOKEN,
});

const thread = await solo.createThread({ agentId: "coder" });

// Wait for the full answer
const result = await solo.ask(thread.id, "What changed in the last deploy?");
console.log(result.answer);

// Or fire and forget, and follow along live
await solo.send(thread.id, "Now draft release notes");
stream.ts
const stream = solo.connect(); // reconnects automatically
stream.subscribe(thread.id);

stream.on((event) => {
  if (event.type === "thread.live") render(event.live);         // streaming text, thinking, tools
  if (event.type === "thread.messages") append(event.messages); // committed messages
});

// later
stream.close();

Embed the core

The runtime, @soloagent/core in packages/core, is a library too. Open it against a data directory and use it in-process, without the HTTP server.

embed.ts
import { SoloAgent } from "@soloagent/core";

const solo = await SoloAgent.open({ dataDir: "./data" });
// … create agents and threads, send messages …
await solo.close();

Durability

Agent runs execute on @earendil-works/pi-durable, Pi's durable execution harness, backed by SQLite in your data directory.

  • Commit before show. Each model turn and each tool call is recorded as a durable step and committed before it's shown in any UI or chat app. Streaming text is saved as it arrives, so a crash loses at most about a second of a half-written answer.
  • Resume after a crash. If the process exits mid-run (a crash, a restart, a deploy), the run resumes from its last committed step when the server starts again. Completed steps aren't repeated. An interrupted model request is retried; a tool call cut off midway runs again only if it's safe to repeat, and otherwise the agent is told it was interrupted.
  • Durable sleep. Scheduled reminders and automations are durable timers. They wait in storage, not in memory, so they still fire after restarts. An automation that came due while the server was down runs once on startup.
  • Durable delegation. ask_agent starts a child conversation that is itself durable. The parent waits for it, across restarts if needed.
  • Visible. The dashboard shows the live durable task graph and upcoming schedules.
Keep the data directory. Durability is only as good as the storage behind it. In the Docker image (Docker, Railway, Render, Fly.io), that's the volume at /data. Elsewhere, make sure SOLOAGENT_DATA_DIR points at persistent storage.

Security

  • One admin token. The dashboard, TUI, API, and WebSocket all require the admin token: SOLOAGENT_TOKEN, or the one generated on first boot. Treat it like a password. The dashboard keeps it in an HTTP-only session cookie.
  • Sealed credentials. Provider keys, OAuth tokens, connector tokens, and webhook secrets are encrypted at rest with AES-256-GCM, using a key derived from SOLOAGENT_SECRET or the secret generated in the data directory.
  • Webhook secrets. Each webhook connector has its own shared secret, sent in x-solo-secret. It grants only that connector's access.
  • Workspace is powerful. The Workspace skill can run shell commands on your server with the server's permissions; its folder is a starting point, not a sandbox. Only enable it for agents that trusted people can reach, and remember that anyone who can message a connector can talk to any agent through it with @handle.
  • Your data stays with you. Threads, memory, schedules, and credentials live in your data directory. Model calls go directly from your server to the providers you connect.
